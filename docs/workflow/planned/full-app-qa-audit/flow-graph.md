# Flow graph

No element is `pass` until every surface its effect reaches has been checked. This file is the map of those connections. It has two parts: the **connection map** (which module writes what, and who reads it) and the **journeys** (ordered end-to-end runs across modules and roles).

The map below is the starting hypothesis built from the docs. Stage 2 of each page audit corrects it from the code: add an edge whenever an element's chain reaches a surface not listed here, and commit the correction. By the end of Phase 2 this file is the verified dependency graph of the product.

## Journeys

Each journey is run as two or more personas in parallel browser contexts, on **L**, at phone width for the guest side and desktop for the host side, then swapped once. Each step lists what to verify beyond the screen. A journey record is saved to `docs/workflow/qa/full-app/journeys/J<nn>-<slug>.md` with a step table (step, actor, action, expected, evidence, verdict).

For every journey also run: the unhappy branch at each decision point, the same journey on Free and on Business, and the read-only persona watching the host side.

## How journeys and page audits share work

- A page audit's Stage 4 may cite a journey step as its evidence for a connected surface, if the journey ran on the same SHA.
- A journey step that fails is filed as a finding against the page that owns the broken link, with the journey ID in the finding.
- If a page audit finds a connection that is on no journey, add it to the map and to the closest journey.
